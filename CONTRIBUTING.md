# Руководство по контрибьюции в проект Deep

Благодарим вас за интерес к проекту Deep! Это руководство поможет вам внести свой вклад в развитие проекта.

## Правила ведения README.md

README.md является основным документом проекта, который должен всегда содержать актуальную информацию. При внесении изменений в проект необходимо обновлять README.md в соответствии со следующими правилами:

1. **Обязательное обновление перед каждым коммитом**:
   - Перед каждым коммитом необходимо убедиться, что README.md содержит актуальную информацию о проекте.
   - Если были добавлены новые функции, они должны быть отражены в разделе API.
   - Если были изменены существующие функции, их описание должно быть обновлено.

2. **Структура README.md**:
   - Введение - краткое описание проекта
   - Установка - инструкции по установке
   - Использование - примеры использования
   - API - документация по методам и классам
   - Архитектура - описание архитектуры проекта
   - Тестирование - информация о тестах
   - Вклад в проект - ссылка на CONTRIBUTING.md
   - Лицензия - информация о лицензии

3. **Документирование API**:
   - Каждый публичный метод должен быть документирован в README.md.
   - Документация должна включать сигнатуру метода, описание, параметры и возвращаемое значение.
   - Для сложных методов должны быть приведены примеры использования.

4. **Примеры кода**:
   - Примеры кода должны быть актуальными и работоспособными.
   - Примеры должны демонстрировать типичные сценарии использования.
   - Сложные примеры должны сопровождаться комментариями.

## Правила ведения audit.md

audit.md содержит анализ безопасности, целостности и производительности проекта. При внесении изменений в проект необходимо обновлять audit.md в соответствии со следующими правилами:

1. **Обязательное обновление перед каждым коммитом**:
   - Перед каждым коммитом необходимо обновить audit.md с учетом внесенных изменений.
   - Аудит должен быть актуальным на момент коммита.
   - Не нужно указывать версию или дату аудита, так как эта информация очевидна из коммита.

2. **Структура audit.md**:
   - Безопасность - анализ безопасности проекта
   - Целостность - анализ целостности системы
   - Производительность - анализ производительности
   - Корректность блокчейн смартконтрактов (если применимо)
   - Известные проблемы - список известных проблем
   - Общие рекомендации - рекомендации по улучшению

3. **Анализ безопасности**:
   - Необходимо проанализировать потенциальные уязвимости.
   - Необходимо предложить рекомендации по устранению уязвимостей.

4. **Анализ производительности**:
   - Необходимо проанализировать производительность критических участков кода.
   - Необходимо предложить рекомендации по оптимизации.

## Процесс внесения изменений

1. **Создание задачи**:
   - Перед началом работы необходимо создать задачу в todo.md.
   - Задача должна содержать четкое описание проблемы или функциональности.

2. **Разработка**:
   - Разработка должна вестись в отдельной ветке.
   - Код должен соответствовать стандартам кодирования проекта.
   - Необходимо писать тесты для новой функциональности.

3. **Тестирование**:
   - Перед отправкой изменений необходимо запустить все тесты.
   - Все тесты должны проходить успешно.
   - Необходимо добавить новые тесты для новой функциональности.

4. **Документирование**:
   - Необходимо обновить README.md и audit.md.
   - Необходимо добавить комментарии JSDoc для новых методов и классов.

5. **Отправка изменений**:
   - Необходимо создать pull request с описанием внесенных изменений.
   - Pull request должен содержать ссылку на задачу.

6. **Ревью кода**:
   - Код должен пройти ревью другими разработчиками.
   - Необходимо исправить все замечания, полученные в ходе ревью.

7. **Слияние изменений**:
   - После успешного ревью изменения могут быть слиты в основную ветку.
   - Необходимо обновить версию проекта в соответствии с правилами версионирования:
     - Для проектов с постфиксом -alpha/beta обновляется номер alpha/beta, а не patch-версия (например, 7.1.0-alpha.0 → 7.1.0-alpha.1).
     - Для стабильных версий используется семантическое версионирование (MAJOR.MINOR.PATCH).

## Стандарты кодирования

1. **Форматирование кода**:
   - Используйте 2 пробела для отступов.
   - Используйте одинарные кавычки для строк.
   - Используйте точку с запятой в конце выражений.
   - Максимальная длина строки - 100 символов.

2. **Именование**:
   - Используйте camelCase для переменных и методов.
   - Используйте PascalCase для классов.
   - Используйте UPPER_CASE для констант.
   - Имена должны быть описательными и отражать назначение.

3. **Комментарии**:
   - Используйте JSDoc для документирования методов и классов.
   - Комментарии должны быть понятными и информативными.
   - Избегайте избыточных комментариев.

4. **Обработка ошибок**:
   - Используйте try-catch для обработки исключений.
   - Возвращайте информативные сообщения об ошибках.
   - Логируйте ошибки для отладки.

## Тестирование

1. **Модульные тесты**:
   - Каждый публичный метод должен быть покрыт модульными тестами.
   - Тесты должны проверять как нормальное поведение, так и обработку ошибок.
   - Используйте моки и стабы для изоляции тестов.

2. **Интеграционные тесты**:
   - Необходимо писать интеграционные тесты для проверки взаимодействия компонентов.
   - Интеграционные тесты должны проверять типичные сценарии использования.

3. **Бенчмарки**:
   - Для критических участков кода необходимо писать бенчмарки.
   - Бенчмарки должны измерять производительность в различных сценариях.

## Документирование

1. **JSDoc**:
   - Каждый публичный метод и класс должен быть документирован с помощью JSDoc.
   - Документация должна включать описание, параметры, возвращаемое значение и исключения.
   - Для сложных методов должны быть приведены примеры использования.

2. **README.md**:
   - README.md должен содержать актуальную информацию о проекте.
   - Документация должна быть понятной и информативной.
   - Примеры кода должны быть актуальными и работоспособными.

3. **audit.md**:
   - audit.md должен содержать актуальный анализ безопасности, целостности и производительности проекта.
   - Анализ должен быть объективным и информативным.
   - Рекомендации должны быть конкретными и реализуемыми.

## Заключение

Соблюдение этих правил поможет поддерживать проект в хорошем состоянии и облегчит работу всех участников. Если у вас есть вопросы или предложения по улучшению этого руководства, пожалуйста, создайте задачу в todo.md.
